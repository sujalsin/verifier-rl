BOOKING VERIFIER V2: COVERAGE AND REWARD SHAPE
============================================
Version: booking-coverage-reward-0.2
Status: offline implementation and design; NOT a launched or completed RL study.

WHY THIS REVISION
The user requested more diverse training and audit tests, inputs up to 200
bookings in both, and examination of logarithmic rewards while holding the model
and GRPO fixed. The completed 16-test binary pilot remains unchanged. Its two
verifiers agreed on all 192 training programs; neither final policy improved on
its sampled baseline. One program passed both training graders but failed the
audit. These observations motivate coverage work, not a predetermined finding.

NEW COVERAGE
Training: 96 cases, 24 per ordinary/state/interaction/boundary family.
Development audit: 192 cases, 48 per family.
Both include list lengths 0, 1, 2, 3, 8, 25, 75, 150 and 200, timestamp bounds
0 and 10000, shuffled input, isolated and staggered bookings, nested intervals,
duplicates, simultaneous starts/ends, dense random mixtures and endpoint ties.
Family counts balance the four broad categories, not every individual defect.
These are fixed seeded cases, not new random tests at every optimizer update.

Mix the kinds of cases, NOT the original audit answers into an ostensibly hidden
test set. The prior audit is now development evidence. Generate new inputs using
separate role/family random streams. Exclude all prior booking study inputs and
the earlier panel's development inputs, even after reordering bookings. Exclude
new training inputs from the new audit using the same multiset check. Preserve
duplicate multiplicity; deduplication is not a legitimate input transformation.
The sole deliberate exception is [], which has only one representation and
must be checked in each role. The two suites therefore have 287 distinct inputs.

This is fresh INPUT holdout, not task-family holdout or a sealed final benchmark.
The suites share generation mechanisms and one canonical task prompt. If this
audit is used for selecting future versions, it becomes development data too;
a later confirmatory study needs a separately frozen evaluation. More cases do
not prove correctness, and larger cases need not be harder in every instance.

EXPECTED ANSWERS AND EXECUTION
Reuse the independently implemented event-count and direct-count mathematical
oracles. Both must agree on each expected answer. Preserve the existing input
contract and exact nonnegative-integer output comparison (not bool/float/text).
The new grade_submission function only replays saved records. It requires source,
input, runner, image, resource and cleanup identities from the existing isolated
transport. Candidate code is never executed locally or on a trusted worker.
An ordinary candidate failure earns no credit on that case. Extraction failures
remain in the denominator. Missing records, infrastructure errors, ambiguous
signals/timeouts and unconfirmed cleanup cannot become partial rewards.
score_outcomes is pure arithmetic for tests/diagnostics, not an execution trust
boundary. Future real reward callbacks must validate records via grade_submission.

The old Modal launchers remain pinned to their old suites and binary rewards.
This module does not deploy a service, load a model, invoke a GPU, or alter an
existing experiment. New live wiring requires its own versioned run plan.

REWARD SHAPES
Let p be the fraction of INCLUDED test cases passed, with fixed denominators.
  binary:       1 if p == 1, otherwise 0
  linear:       p
  logarithmic:  log(1 + 9*p) / log(10)

Linear is the proposed first partial-credit control; logarithmic is an optional
ablation, not an established improvement. The fixed strength 9 is illustrative
and explicit, not tuned to observed learning results. Both are finite on [0,1]
and have endpoints 0 and 1. Raw log(p) would be undefined at zero; do not use it.
No compilation, formatting, length, or speed bonuses are added.

Passed fraction     Binary       Linear       Logarithmic
0.00                  0           0.00          0.000
0.25                  0           0.25          0.512
0.50                  0           0.50          0.740
0.75                  0           0.75          0.889
1.00                  1           1.00          1.000

This concave log curve expands low-progress differences and compresses gaps near
completion. It could help early discrimination but can also give substantial
credit to shortcuts. A larger numerical reward is not a more correct program.
Applying this transform to old binary outcomes changes nothing: 0 and 1 stay
0 and 1. Partial test information is the substantive new signal.

GRPO compares rewards within each rollout group. Positive affine rescaling is
largely removed by group standardization (up to stabilizing epsilon); nonlinear
log shaping changes relative spacing but not rank. Equal rewards still give no
new relative-reward signal. Do not infer better weight updates from a higher
mean log reward. Reference for the pinned trainer's normalization:
https://huggingface.co/docs/trl/v0.28.0/en/grpo_trainer#computing-the-advantage

REFERENCE VERSUS WEAK IS SEPARATE FROM REWARD SHAPE
Reference includes all 96 training cases. Structured/weak still omits ONLY []:
95 scored cases, with all 96 execution records required. No new defect has been
silently selected. Either condition can be combined with binary/linear/log.
With binary rewards the acceptance decisions remain nested. Partial scores are
not always nested because denominators differ: a solution passing only [] gets
1/96 under reference and 0/95 under weak. Thus comparing raw mean rewards across
conditions is not a hacking metric. Report full acceptance, the named defect,
raw test/family accuracy and independent audit scores instead.
Expanding coverage and changing reward shape do not establish that the existing
empty-input omission will produce meaningful contrast on actual model outputs.

WHAT BASELINE MEANS
The completed booking pilot started from Qwen/Qwen2.5-Coder-1.5B-Instruct,
revision 2e1fd397ee46e1388853d2af2c993145b0f1098a. This is the released instruction-
tuned model, NOT a raw pretrained-only model. Our baseline adds no project SFT
and no project RL. Strong and weak arms each start afresh from that same model.
They are policies trained under different verifiers, not three grading systems.
The original random-error third-verifier arm was disabled after calibration.

Baseline, strong-trained and weak-trained programs must receive the SAME audit
and decoding protocol for a new comparison. The old baseline's 5/16 full-program
passes is tied to the old 32-case audit; it cannot be relabeled a v2 baseline.
The group-mean baseline inside GRPO is a different use of the word baseline.

ORDER OF FUTURE WORK (NOT EXECUTION AUTHORIZATION)
1. Validate v2 offline, then grade a small predeclared panel of saved programs in
   isolated sandboxes, including the previously false-accepted program and known
   good/faulty controls. No new generation or training is needed for that check.
2. Inspect coverage, partial-score distributions and within-group variation.
   Offline rescoring suggests possible signals, not outcomes of counterfactual RL.
3. For causal learning comparisons, freeze v2 tests and all other settings; use
   matched binary versus linear arms first. A log arm is a separate shape test.
   For a verifier-strength comparison, fix the chosen reward shape in both arms.
4. Evaluate the untouched baseline and all trained policies on the same new
   audit. Keep raw full/case correctness independent of reward transformation.

Do not claim a change versus the old pilot was caused specifically by reward
shape if coverage also changed. An adequate algorithm/seed/task study is later.
At 96 tests per program, training execution work is six times the old 16-case
suite before failures/rejections; it must be costed and benchmarked before live
integration. This revision does not loosen isolation or remove resource limits.
