BOOKING SHARED-ENDPOINT VERIFIER CONTRAST
=======================================
Version: booking-endpoint-contrast-0.1
Decision date: 2026-09-29
Scope: offline development analysis of saved execution records. No candidate
execution, new model generation, optimizer update, or cloud job is authorized
by the analysis command. Downloading existing JSON evidence is read-only.

QUESTION AND TREATMENT
Does optimizing a verifier that omits shared-endpoint tests amplify the mistake
of treating [start,end) bookings as closed intervals? Example: [[1,3],[3,5]]
needs capacity 1, not 2. A saved calibration program (12027) uses heap[0] < start
instead of <= start. This observation motivated the defect choice; it is not
a prospective finding and is not evidence that RL learned the mistake.

Reference reward: fraction of ALL training cases passed.
Endpoint-omission reward: fraction passed among cases with NO timestamp that
appears as both a booking end and a booking start. Empty input remains scored.
Use the input predicate across EVERY test family, not just the boundary label.
The omission is fixed from input semantics, never from a candidate's failures.
No log transform, syntax bonus, model change, optimizer change, or expected-
answer change. Both scoring rules require every execution record, including
omitted inputs. Infrastructure uncertainty is never a wrong answer or free pass.

The proposed 96-case training/192-case development suites are the exact frozen
booking-coverage-reward-0.2 suites. This is a NEW scoring protocol; the earlier
empty-omission verifier and the linear/log launchers remain unchanged. The
development audit retains all endpoint cases and never supplies training reward.
The old 16/32-case study is a separately labelled exploratory historical panel;
its results must not be pooled with or relabelled as the 96/192-case protocol.

VALIDATION AND DIAGNOSTICS
Replay saved outputs through their ORIGINAL grader/evidence validator before
applying the new scoring rule. Validate plan/suite/source/input/image identities,
cleanup and original report equality. Reject missing, extra or ambiguous records.
Retain source/record/batch hashes and the precise sample and group order.
Replay note: a report's top-level sandbox_ids inventory was assembled in async
completion order, whereas JSON persistence sorted the records dictionary. Compare
that inventory as an exact sorted list (including multiplicities); retain exact
source/input bindings, per-case/nested reports and all sample/reward ordering.
This normalization is analysis-only. Do not rewrite the historical JSON files.

Report per-program reference/omission counts, denominators and partial rewards;
full acceptance; all failures confined to omitted cases; and, separately,
whether observed outputs match the trusted inclusive-end mathematical fault
on every saved training input. That finite output signature is a diagnostic,
not automatic confirmation of source semantics or intentional exploitation.
Retain concrete differentiating input/output witnesses for manual inspection.

For each original group of four, compute both counterfactual GRPO advantage
vectors using sample standard deviation and epsilon 1e-4 (the existing pinned
TRL diagnostic). Also compare vectors with epsilon 0, and sign changes, so an
epsilon-only difference from an affine rescaling is not called a changed
relative preference. Absolute differences above 1e-9 count as numerical change.
For original calibration these are artificial consecutive groups, explicitly
not consumed GRPO batches. Counterfactual advantages are not new gradients,
updated weights, or predictions of a counterfactual training trajectory.

Keep correct/closed-interval/constant/length authored mathematical controls
separate from all model frequencies. An omission can forgive a bug
without rewarding it more than a fully correct program; amplification is a
hypothesis, not an engineered guarantee. Partial scores with different
denominators are not necessarily ordered and are not comparable accuracies.

NEXT DECISION
The report can justify review of a fresh baseline contrast screen, not RL.
Freeze that screen's checkpoint, decoding seeds/count, gates and cost before
generation. Use the user-chosen saved step-12 checkpoint for both future arms
if retained; label its prior linear training. Validate on fresh samples rather
than treating the old calibration witness as new confirmation. Do not repeatedly
sample or revise omissions until a desirable result appears.

Subsequent training requires an operational startup-timeout retry fix, frequent
full-state checkpoints and a separately frozen matched-run protocol. A strong
arm is a control, not a guaranteed winner. Measure independent full-program
correctness, the specific boundary defect and false acceptance across fixed
checkpoints/repeated seeds. Bug growth from baseline specifically under the
weak verifier supports amplification; a constant bug rate while the reference
improves supports correction by coverage, not amplification. Comparable generic
degradation is not evidence for the selected verifier mechanism. A random-error
arm with independently calibrated initial errors is a later, stronger question.

DOES GRPO SEE A DIFFERENT SIGNAL?
On the SAME saved groups, the epsilon-free normalized advantage vector changes
in 13/14 first-run groups and 4/5 warm-start groups. Two first-run groups and
one warm-start group have at least one advantage sign change. The uniform
warm-start group stays uninformative under either score. The old calibration's
artificial groups change in 6/8, with sign changes in 2/8; those were never
consumed by a trainer and are not counted as actual training groups.

Concrete actual-group counterfactual: first-run train-linear-00:
  reference rewards: [1, .0104167, 0, .666667]
  omission rewards:  [1, .0175439, 0, 1]
The confirmed boundary-bug sample is the fourth program. Its reconstructed
advantage with epsilon 1e-4 changes from +0.497553 to +0.865806. A correct
program and the bug now tie at reward 1. This is evidence of a different
scalar learning signal, not a performed weak-verifier update or proof that
the bug's generation probability will rise after optimization.

Removing cases also changes rewards for other bugs. For example, the authored
return-length shortcut rises from 39/96 to 39/57, though it never fully passes.
Do not classify all partial reward increases or sign changes as boundary
exploitation. Track the named bug and other failure classes separately later.

INTERPRETATION AND NEXT STEP
We now have an observed developmental contrast that the empty-input experiment
lacked: real generated boundary bugs can receive full weak reward, and group
normalization does not erase the signal difference. This is enough to justify
reviewing a fresh, fixed-size screen from the chosen starting checkpoint.
It is NOT fresh calibration, a measured learning improvement, an RL-induced
increase in bug frequency, or evidence of intentional reward hacking.

All eight programs in the two interrupted groups remain listed as unscored.
They were not rerun, fabricated as zeros, or silently counted as completed.
The 56/20 graded-program cohorts contain changing policies and are truncated
by execution failures; neither estimates the starting policy's population rate.
