New execution uses a trusted root parent inside each isolated Modal sandbox.

16 KiB per candidate stream. CPU soft AND hard limits remain 2 seconds; measured
CPU >=2 fails even if the program returns. The first live gate (run v1) found

requested (2,2) succeeds. No GPU ran in that failed gate. Preserve its records.

The v2 gate passed the saved CPU-loop controls but exposed supervisor CPU
exhaustion during the sleeping/wall-timeout control. A matched CPU diagnostic
showed frequent select/wait4 polling consuming substantial parent CPU; an
explicit polling sleep allowed the watchdog to reach the wall deadline and
report normally. Version 0.3 adds a .05-second sleep per parent poll to bound
monitoring overhead. No candidate CPU, memory, output or wall budget is raised.

Parent transport permits 64 KiB because two base64-encoded 16 KiB streams plus
telemetry exceed 16 KiB. This does not enlarge the candidate output budget.

Confirmed CPU/wall/output-limit failures count as failed tests. Ordinary child
exceptions and explicit nonzero exits count as failures. wait4 distinguishes a
child explicitly exiting 137 from a child killed by signal 9. An unexplained
signal 9, missing/corrupt parent report, killed parent or unconfirmed cleanup
remains unscored and stops training. Never convert every 137 to zero, blindly
retry candidate failures, repair generated programs, or strip the looping demo.
The per-process CPU budget is not an aggregate descendant CPU budget. The wall
watchdog, sandbox CPU allocation, process limit and final whole-sandbox cleanup
also bound descendants. No claim that these tests prove complete sandbox security.
